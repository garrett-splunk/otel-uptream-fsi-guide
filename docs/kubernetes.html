Path B · Kubernetes · us1

Deploy the OpenTelemetry Demo to Kubernetes

The same demo shown to the customer: about twenty microservices already instrumented with OpenTelemetry, sending OTLP to an in-cluster Collector that tags every signal and exports to Splunk Observability Cloud.

About 40 minutes · a Kubernetes cluster with kubectl and helm · an ingest token

How this relates to Path A

This is the Collector design from Path A, running as a Kubernetes agent: the apps carry no token, and only the Collector holds it. To compare it with SDK-direct export, use Path A.

Already running OpenTelemetry in a cluster?

You do not need the demo. Skip to Steps A to G to add Splunk Observability Cloud as a second destination on the Collector you already have, without changing your existing pipelines.

Want to search logs that are already in Splunk Enterprise?

See Steps H to M to connect Splunk Enterprise to Observability Cloud in realm us1 with Log Observer Connect.

Based on the OpenTelemetry Kubernetes Demo guide

The steps and commands follow the OpenTelemetry Kubernetes Demo workshop guide, adapted so you can run it on your own cluster. That guide assumes a prepared workshop host where REALM, ACCESS_TOKEN and INSTANCE are already set. Here you set them yourself in Step 1.

Step 1~5 min

Pre-flight

You need a Kubernetes cluster you can reach with kubectl, plus helm and git. The workshop used a three-node k3d cluster; kind, minikube or a cloud cluster also work. The full demo needs roughly 9 to 10 GB of memory. With about 8 GB (for example minikube on Docker Desktop at its default size), use lite mode in Step 3. Check the OpenTelemetry Demo requirements for details.

bash
kubectl get nodes
expected output
NAME                            STATUS   ROLES                  AGE   VERSION
k3d-shw-455e-cluster-agent-0    Ready    <none>                 5d    v1.33.4+k3s1
k3d-shw-455e-cluster-agent-1    Ready    <none>                 5d    v1.33.4+k3s1
k3d-shw-455e-cluster-server-0   Ready    control-plane,master   5d    v1.33.4+k3s1

Set three variables, and where the token goes

The install command in Step 4 reads three shell variables. They live only in your terminal session, so there is no file to leak.

bash
export REALM=us1
read -rs ACCESS_TOKEN && export ACCESS_TOKEN     # paste your INGEST token, press Enter (it is not echoed)
export INSTANCE=northstar-01                      # short id: lowercase letters, digits, hyphens
bash
echo "REALM=$REALM"
[ -n "$ACCESS_TOKEN" ] && echo "TOKEN: set" || echo "TOKEN: MISSING"
echo "INSTANCE=$INSTANCE"
Key idea

INSTANCE becomes lab.id. Resource attributes on the Collector tag every signal with it, so you can filter to your demo in Observability Cloud even if other people share the org.

Token type

Use an org access token with the Ingest scope. An API-scope token returns 401 at the ingest endpoint.

Step 3~5 min

Create splunk-values.yaml

This file adds two Splunk exporters and a processor to the demo's Collector and wires them into the traces and metrics pipelines. Save it as splunk-values.yaml in the opentelemetry-demo directory.

Empty strings are intentional

Realm, token and resource attribute values are injected at install time by the --set-string flags in Step 4. You do not paste secrets into this file.

Chart version matters

This values file is written for demo chart opentelemetry-demo 0.42.x (demo 3.1.0), which uses snake_case Collector names such as otlp_http, resource_detection and span_metrics. Older chart versions use otlphttp, resourcedetection and spanmetrics. If the Collector crash-loops with references receiver "spanmetrics" which is not configured, your chart and values file are from different eras. Run helm show values open-telemetry/opentelemetry-demo and copy the component names from the opentelemetry-collector.config section.

Small cluster? Use lite mode

The full demo asks for roughly 9 to 10 GB of memory and about 30 pods. On a laptop cluster with about 8 GB, add a second values file, lite-values.yaml, that turns off Grafana, Jaeger, Prometheus, OpenSearch and the AI chatbot components and exports only to Splunk. Keep astronomy-db enabled, because product-catalog waits for it at startup. Both files are in the k8s/ folder of the lab repo.

splunk-values.yaml
opentelemetry-collector:
  config:
    exporters:
      otlp_http/signalfx:
        traces_endpoint: ""
        headers:
          X-SF-Token: ""
          Content-Type: "application/x-protobuf"
        sending_queue:
          batch: {}
      signalfx:
        realm: ""
        access_token: ""
    processors:
      resource/lab:
        attributes:
          - key: lab.id
            value: ""        # Index [0]
            action: upsert
          - key: lab.owner
            value: ""        # Index [1]
            action: upsert
          - key: k8s.cluster.name
            value: ""        # Index [2]
            action: upsert
          - key: deployment.environment
            value: ""        # Index [3]
            action: upsert
    service:
      pipelines:
        traces:
          processors: [memory_limiter, resource_detection, resource, resource/lab, transform/sanitize_spans, gen_ai_normalizer, transform/redact_sensitive_data, redaction]
          exporters: [otlp_grpc/jaeger, debug, span_metrics, otlp_http/signalfx]
        metrics:
          receivers: [otlp, kafkametrics, span_metrics, prometheus/ad]
          processors: [memory_limiter, resource_detection, resource, resource/lab]
          exporters: [otlp_http/prometheus, debug, signalfx]
        logs:
          processors: [memory_limiter, resource_detection, resource, resource/lab, transform/sanitize_logs]
          exporters: [opensearch, debug]

The attribute index in the install command refers to the position of each attribute above:

IndexKeySet at install to
[0]lab.id${INSTANCE}
[1]lab.owneryour name, no spaces
[2]k8s.cluster.name${INSTANCE}-cluster
[3]deployment.environmentk8s-workshop-${INSTANCE}

Why these endpoints: traces use the same OTLP/HTTP ingest path as Path A (/v2/trace/otlp, with the X-SF-Token header). This guide's tested config sends metrics through Splunk's signalfx exporter, which needs only the realm and token. Sending metrics as OTLP to /v2/datapoint/otlp (Path A) is also supported.

Logs stay in the demo

The logs pipeline goes to the demo's own OpenSearch and the debug exporter, not to Splunk. Splunk Log Observer is not part of this setup. To search logs that already live in Splunk Enterprise, see Log Observer Connect (Steps H to M).

Step 4~10 min

Install

Shortcut: the lab repo script

k8s/install.sh runs this same helm upgrade --install for you. It reads SPLUNK_REALM and SPLUNK_ACCESS_TOKEN from the repo's .env, picks lite mode automatically on small clusters, and sets the environment to k8s-workshop-<INSTANCE>. Run LAB_OWNER=yourname ./k8s/install.sh.

Set lab.owner to your name

Replace <your name, no spaces> in the command below. It is how you will find your application in Observability Cloud.

bash
helm install otel-demo open-telemetry/opentelemetry-demo \
  -n otel-demo --create-namespace \
  -f splunk-values.yaml \
  --set-string "opentelemetry-collector.config.exporters.otlp_http/signalfx.traces_endpoint=https://ingest.${REALM}.signalfx.com/v2/trace/otlp" \
  --set-string "opentelemetry-collector.config.exporters.otlp_http/signalfx.headers.X-SF-Token=${ACCESS_TOKEN}" \
  --set-string "opentelemetry-collector.config.exporters.signalfx.realm=${REALM}" \
  --set-string "opentelemetry-collector.config.exporters.signalfx.access_token=${ACCESS_TOKEN}" \
  --set-string "opentelemetry-collector.config.processors.resource/lab.attributes[0].value=${INSTANCE}" \
  --set-string "opentelemetry-collector.config.processors.resource/lab.attributes[2].value=${INSTANCE}-cluster" \
  --set-string "opentelemetry-collector.config.processors.resource/lab.attributes[3].value=k8s-workshop-${INSTANCE}" \
  --set-string "opentelemetry-collector.config.processors.resource/lab.attributes[1].value=<your name, no spaces>"

The traces endpoint above uses the signalfx.com hostname that this demo was tested with. For us1 the equivalent newer hostname is ingest.us1.observability.splunkcloud.com; both are accepted.

Step A~10 min

Point an existing OpenTelemetry cluster at Splunk

Path B above installs the demo with its own Collector. If your cluster already runs OpenTelemetry and ships to another backend (Jaeger, Tempo, Prometheus, another vendor), you do not reinstall anything. You add Splunk Observability Cloud as one more destination on the Collector that is already there. Steps A to G do this without editing your existing pipelines, so the current backend keeps receiving data while you compare.

What was and was not tested

The upstream opentelemetry-collector Helm chart was rendered with helm template at versions 0.110.0 and 0.178.2: the new pipelines appear next to the existing ones, and the token environment variables render from a Secret. The ingest endpoints were verified live in Path A (SDK direct to us1), and the demo's own Collector sent live traces and metrics in Steps 1 to 7. The exact otlphttp/splunk block below has not been run on a live Collector, and the Operator and plain-manifest variants are untested. Step D includes a dry run so you can check before anything changes.

Before you start

  • Complete Step 1 so REALM and ACCESS_TOKEN (an Ingest-scope token) are set in this terminal.
  • You can run kubectl and helm against the cluster, with permission to upgrade the Collector release and create a Secret in its namespace.

Find what you already have

bash
export NS=observability          # namespace where your Collector runs
export RELEASE=otel-collector    # Helm release name of that Collector
helm list -A | grep -i -E 'otel|collector'
kubectl -n $NS get deploy,ds,sts -o wide
helm get values $RELEASE -n $NS -o yaml > current-values.yaml   # backup; may hold tokens, do not commit

Not using Helm?

With the OpenTelemetry Operator, put the same exporters, processors and service.pipelines blocks from Step C under spec.config of the OpenTelemetryCollector resource, and the two environment variables under spec.env. With plain manifests, edit the Collector ConfigMap, add the two variables to the container env, then run kubectl -n $NS rollout restart on the workload. Step B~2 min

Store the token as a Secret

Store the token in a Kubernetes Secret in the Collector's namespace. The Collector reads it as an environment variable, so the token never appears in your Helm values.

bash
kubectl -n $NS create secret generic splunk-o11y-token --from-literal=token="$ACCESS_TOKEN"
kubectl -n $NS get secret splunk-o11y-token
expected output
NAME                TYPE     DATA   AGE
splunk-o11y-token   Opaque   1      3s
Why a Secret

Helm records the values a release was installed with in a Secret, so a token passed with --set-string is readable by anyone who can read Secrets in that namespace. A secretKeyRef keeps the token in one object that you can lock down and rotate. See Adapting for a customer cluster.

Step C~5 min

Add Splunk as a second destination

Create a values file that only adds to your release. The two new pipelines, traces/splunk and metrics/splunk, read from your existing receiver and write to Splunk. Your existing traces and metrics pipelines are not in this file, so they stay as they are.

bash
cat > add-splunk.yaml <<'EOF'
extraEnvs:
  - name: SPLUNK_REALM
    value: us1                      # your realm
  - name: SPLUNK_ACCESS_TOKEN
    valueFrom:
      secretKeyRef:
        name: splunk-o11y-token
        key: token

config:
  processors:
    batch: {}
    resource/splunk:
      attributes:
        - key: deployment.environment
          value: eks-prod-east      # name this cluster or environment
          action: insert            # only sets it when the app did not
  exporters:
    otlphttp/splunk:
      traces_endpoint: https://ingest.${env:SPLUNK_REALM}.observability.splunkcloud.com/v2/trace/otlp
      metrics_endpoint: https://ingest.${env:SPLUNK_REALM}.observability.splunkcloud.com/v2/datapoint/otlp
      headers:
        X-SF-Token: ${env:SPLUNK_ACCESS_TOKEN}
  service:
    pipelines:
      traces/splunk:
        receivers: [otlp]
        processors: [resource/splunk, batch]
        exporters: [otlphttp/splunk]
      metrics/splunk:
        receivers: [otlp]
        processors: [resource/splunk, batch]
        exporters: [otlphttp/splunk]
EOF

The quoted 'EOF' matters: it stops the shell from expanding ${env:...}, which the Collector resolves at startup. Edit the realm and the environment name before you save.

What each part does

BlockPurpose
extraEnvsGives the Collector SPLUNK_REALM and the token from the Secret in Step B.
otlphttp/splunkSends traces to /v2/trace/otlp and metrics to /v2/datapoint/otlp on ingest.<realm>.observability.splunkcloud.com, with the token in the X-SF-Token header. The older signalfx.com hostname still works.
resource/splunkAdds deployment.environment so the services show under an environment in APM. insert never overwrites a value the application already set.
traces/splunk, metrics/splunkNew pipelines. Because they are new keys, Helm adds them without touching your existing pipelines.
If extraEnvs is already set

Helm replaces a list instead of merging it, so the extraEnvs above would drop your existing entries. Open current-values.yaml, copy your existing entries into add-splunk.yaml under extraEnvs, and keep the two SPLUNK_* entries.

Exporter name depends on the Collector version

Older Collectors, including the 0.116.0 build used in Path A, call the exporter otlphttp. Newer releases call it otlp_http. With the Helm chart you can keep writing otlphttp/splunk: both chart versions I rendered accepted it, and 0.178.2 rewrote it to otlp_http/splunk in the final config. With the Operator or a plain ConfigMap there is no rewrite, so use the name your Collector version expects. A wrong name fails at startup with unknown type.

Other things to adjust

If your receiver is not named otlp, change it in both pipelines. If your metrics come from a scrape receiver such as prometheus, add it to the receivers list of metrics/splunk. Only signals that arrive at the Collector can be forwarded. If your existing pipelines use memory_limiter, add it first in the processors list of both new pipelines.

Step D~5 min

Apply with Helm

Find your chart version in the CHART column of helm list -n $NS (for example opentelemetry-collector-0.178.2 means 0.178.2). Pinning it keeps the upgrade to your additions only.

bash
export CHART_VERSION=0.178.2     # your installed chart version
helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
helm repo update

First, a dry run. It renders the result without changing the cluster, and the filter shows only the lines you care about:

bash
helm upgrade $RELEASE open-telemetry/opentelemetry-collector -n $NS \
  --version $CHART_VERSION --reuse-values -f add-splunk.yaml --dry-run \
  | grep -E "traces/splunk|metrics/splunk|SPLUNK_|splunk-o11y-token"

You should see both new pipelines and the Secret reference. If the command errors, fix it now, before the real upgrade. Then apply:

bash
helm upgrade $RELEASE open-telemetry/opentelemetry-collector -n $NS \
  --version $CHART_VERSION --reuse-values -f add-splunk.yaml

The chart adds a checksum of the config to the pod template, so the Collector pods restart on their own. Watch them, then check the logs for export problems:

bash
kubectl -n $NS get pods -w          # wait for the new pods to be Running
kubectl -n $NS logs -l app.kubernetes.io/instance=$RELEASE --tail=50 \
  | grep -iE "error|401|404|unknown type|not configured"
expected output
# (no matching lines: silence is good)
Release from a different chart?

Replace open-telemetry/opentelemetry-collector with the chart your release uses (helm list shows it), and keep --version and --reuse-values. Check that its values use the same config:, extraEnvs: structure; some vendor charts name these differently.

Step F~10 min

Applications that send straight to the old backend

Skip this step if your applications already send to the Collector. If they send straight to the old backend, you have two options.

Option 1 (recommended): send through the Collector

Point the applications' OTLP exporter at the Collector. Find the Collector Service first:

bash
kubectl -n $NS get svc | grep -i collector
bash
export APP_NS=shop              # namespace of the application
export APP=checkout            # Deployment name
export COLLECTOR_SVC=otel-collector   # Service name from the command above
kubectl -n $APP_NS set env deploy/$APP \
  OTEL_EXPORTER_OTLP_ENDPOINT=http://$COLLECTOR_SVC.$NS.svc.cluster.local:4318 \
  OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
Keep the old backend fed

Once an application sends to the Collector, the Collector decides where its data goes. Add your old backend as an exporter on the Collector too, in your existing pipelines, or the old backend stops receiving that application's data. If the old backend was the application's direct target, copy that endpoint into an exporter and add it to the original traces and metrics pipelines.

Option 2: send straight to Splunk

Use the signal-specific variables with full URLs, so the SDK does not append /v1/traces. This puts the token in every application that uses it, so prefer Option 1 for anything beyond a test. The mechanics and trade-offs are in Path A, Challenge 1.

bash
kubectl -n $APP_NS create secret generic splunk-o11y-otlp-headers \
  --from-literal=OTEL_EXPORTER_OTLP_HEADERS="X-SF-Token=$ACCESS_TOKEN"
kubectl -n $APP_NS set env deploy/$APP --from=secret/splunk-o11y-otlp-headers
kubectl -n $APP_NS set env deploy/$APP \
  OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf \
  OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=https://ingest.$REALM.observability.splunkcloud.com/v2/trace/otlp \
  OTEL_EXPORTER_OTLP_METRICS_ENDPOINT=https://ingest.$REALM.observability.splunkcloud.com/v2/datapoint/otlp \
  OTEL_RESOURCE_ATTRIBUTES=deployment.environment=eks-prod-east

The Secret's key is the variable name, so set env --from=secret/... injects OTEL_EXPORTER_OTLP_HEADERS without the token appearing in the Deployment spec. Each set env triggers a rollout of that Deployment. These two commands have not been run against a live cluster.

Step G~5 min

Cut over, or roll back

Run both destinations side by side for as long as you want to compare. When the customer is satisfied, you can stop sending to the old backend, or keep both. To stop, edit the file that holds the complete values for the release (a stable copy is the current-values.yaml you saved in Step A, with your additions merged in). Do not use --reuse-values here, because the file is now the full set.

  1. Export the current values: helm get values $RELEASE -n $NS -o yaml > cutover-values.yaml.
  2. In cutover-values.yaml, under config.service.pipelines.traces and metrics, replace the old exporter with otlphttp/splunk and add resource/splunk to each processors list.
  3. Delete the traces/splunk and metrics/splunk blocks and the old exporter definition.

The pipelines then look like this (your processor and receiver names may differ):

yaml
config:
  service:
    pipelines:
      traces:
        receivers: [otlp]
        processors: [memory_limiter, resource/splunk, batch]
        exporters: [otlphttp/splunk]
      metrics:
        receivers: [otlp]
        processors: [memory_limiter, resource/splunk, batch]
        exporters: [otlphttp/splunk]

Check the render, then apply. A values file with the full config renders cleanly on chart 0.178.2:

bash
helm upgrade $RELEASE open-telemetry/opentelemetry-collector -n $NS --version $CHART_VERSION -f cutover-values.yaml --dry-run | grep -A12 -E "^        (traces|metrics):"
helm upgrade $RELEASE open-telemetry/opentelemetry-collector -n $NS --version $CHART_VERSION -f cutover-values.yaml

Roll back

Any time something looks wrong, return to the previous revision:

bash
helm history $RELEASE -n $NS
helm rollback $RELEASE <REVISION> -n $NS          # pick the revision before your change

To remove the token completely, run kubectl -n $NS delete secret splunk-o11y-token, then rotate or delete the token in Splunk (Settings → Access Tokens).

Troubleshooting this section

SymptomFix
401 UnauthorizedThe token is not an Ingest-scope token, or the Secret holds a different value. Recreate the Secret and restart the pods.
unknown type: "otlphttp" or unknown type: "otlp_http"The exporter name does not match the Collector version. Use the other spelling, or the Helm chart, which rewrites it.
references exporter "otlphttp/splunk" which is not configuredThe exporter block is missing or misspelled under config.exporters. Re-check add-splunk.yaml.
404 ... /v1/metrics or /v1/tracesThe exporter was given endpoint instead of traces_endpoint and metrics_endpoint. Use the full URLs from Step C.
Existing backend stopped receiving dataA pipeline's exporters list was replaced without the old exporter. Restore the old exporter in that list, or helm rollback.
SPLUNK_ACCESS_TOKEN is empty, or your other variables disappearedextraEnvs was replaced, not merged. Copy your existing entries into add-splunk.yaml (Step C) and upgrade again.
No errors, but nothing in APMThe applications are not sending to this Collector, or the receiver name in the new pipelines is wrong. Check the Collector logs for received spans, and confirm the Step F variable.
Services appear without an environmentSet deployment.environment in the resource/splunk processor, or in the application's OTEL_RESOURCE_ATTRIBUTES.
Pods crash-loop after the upgradeRead the first error in kubectl -n $NS logs <pod>, fix the config, or helm rollback $RELEASE <REVISION> -n $NS.
Cost and limits

Sending to a second backend doubles the Collector's outbound traffic and its CPU for the Splunk pipelines. Check the org's entitlements before pointing production traffic at a trial or Free Edition org.

Step H~10 min

Add Splunk Enterprise logs with Log Observer Connect (us1)

Log Observer Connect lets Splunk Observability Cloud search logs that already live in Splunk Enterprise, next to your metrics and traces. Observability Cloud uses the Splunk Enterprise search head to authenticate a service account and to run the searches. Your logs stay in Splunk Enterprise; Log Observer Connect does not store or index them, and the documentation lists no additional charge for it.

Source and status of this section

Written from the Splunk documentation Set up Log Observer Connect for Splunk Enterprise and Configure and install certificates for Log Observer Connect, read on 10 November 2026. It has not been run against a live Splunk Enterprise instance. The OpenSSL commands in Step K were run locally with a throwaway CA to check the file order and the first-certificate extraction. Settings change between releases, so use the current documentation as the reference.

Is it available in your org?

Log Observer Connect is supported in realm us1, with Splunk Enterprise 9.0.1 or higher. It is not available for Splunk Cloud Platform trials, and it cannot read logs from a GovCloud environment. The documentation does not say whether Free Edition orgs can add this connection, so open Logs → Logs connections in the org first and confirm that Add new connection is offered before you promise it to a customer.

How this differs from the Collector path

The Collector steps earlier in this page send telemetry to Splunk Observability Cloud. Log Observer Connect works the other way: Observability Cloud reaches into a Splunk Enterprise you already run. The demo's logs go to its own OpenSearch, not to Splunk Enterprise, so they will not appear here unless you also send them to Splunk Enterprise (for example with the Splunk HEC exporter).

Step I~10 min

Sizing the search limit

Each active Log Observer Connect user triggers about four back-end searches whenever they search. Multiply your number of users by 4 for the Standard search limit: 10 users gives 40, 20 users gives 80. Three people searching at the same moment cause about 12 searches in Splunk Enterprise, all under this one account.

Then create the user: Settings → Users → New user. Give it a strong password and assign the role you just created. Make sure token authentication is active for this account, as the prerequisite above says; if the connection later fails to authenticate, check this first.

Step J~5 min

Limit long searches with a workload rule

Add a workload rule that stops any search by the service account that runs longer than five minutes. It keeps Log Observer Connect responsive and makes it less likely that its searches queue. In Splunk Enterprise, create it under Settings → Workload Management → Workload Rules, following Create a Workload Rule in Splunk Web in the Splunk Enterprise documentation, with these values:

FieldValue
Predicateuser=<your_Log_Observer_Connect_service-account_name> AND runtime>5m
ScheduleAlways on
ActionAbort search

Replace the placeholder with the username from Step I. After you save, the rule shows on the Workload Rules tab.

Step K~20 min

Secure the management port with a certificate

Log Observer Connect secures the connection to your management port (8089) with a certificate you install on the search head. You have two options: sign one yourself (fastest, fine for a lab) or get one from a certificate authority such as Let's Encrypt or Sectigo (the more secure choice). The commands below follow the Splunk documentation for the self-signed route and use $SPLUNK_HOME/etc/auth/sloccerts, a new directory, so they do not overwrite the certificates that ship with Splunk Enterprise.

1. Create a certificate authority

bash
mkdir $SPLUNK_HOME/etc/auth/sloccerts
cd $SPLUNK_HOME/etc/auth/sloccerts

$SPLUNK_HOME/bin/splunk cmd openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -aes-256-cbc -out myCAPrivateKey.key
# enter a password when prompted

$SPLUNK_HOME/bin/splunk cmd openssl req -new -key myCAPrivateKey.key -out myCACertificate.csr -addext "basicConstraints=critical,CA:TRUE" -addext "keyUsage=critical,keyCertSign,cRLSign"
# enter the key password; leave Common Name blank

echo -e "# root-ssl-extensions.cnf\n[v3_ca]\nbasicConstraints = critical,CA:TRUE\nkeyUsage = critical,keyCertSign,cRLSign\nsubjectKeyIdentifier = hash" > root-ssl-extensions.cnf

$SPLUNK_HOME/bin/splunk cmd openssl x509 -req -in myCACertificate.csr -signkey myCAPrivateKey.key -extensions v3_ca -extfile ./root-ssl-extensions.cnf -out myCACertificate.pem -days 3650
# enter the key password

2. Create and sign the server certificate

When the req -new command asks for a Common Name, enter the host name you will use in the Splunk platform URL. The documentation only says to leave the Common Name blank for the authority, not for the server certificate.

bash
$SPLUNK_HOME/bin/splunk cmd openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -aes-256-cbc -out mySplunkWebPrivateKey.key
# enter a password when prompted

# Splunk Web does not support password-protected keys, so remove the password:
$SPLUNK_HOME/bin/splunk cmd openssl pkey -in mySplunkWebPrivateKey.key -out mySplunkWebPrivateKey.key.nopass && mv mySplunkWebPrivateKey.key.nopass mySplunkWebPrivateKey.key
$SPLUNK_HOME/bin/splunk cmd openssl pkey -in mySplunkWebPrivateKey.key -check -noout

$SPLUNK_HOME/bin/splunk cmd openssl req -new -key mySplunkWebPrivateKey.key -out mySplunkWebCert.csr -addext "basicConstraints = critical,CA:FALSE" -addext "keyUsage = critical,digitalSignature,keyEncipherment" -addext "extendedKeyUsage = serverAuth,clientAuth"

echo -e "#server-ssl-extensions.cnf \n[v3_srv]\n basicConstraints = critical,CA:FALSE\nkeyUsage = critical,digitalSignature,keyEncipherment\n extendedKeyUsage = serverAuth,clientAuth\n" > server-ssl-extensions.cnf

$SPLUNK_HOME/bin/splunk cmd openssl x509 -req -in mySplunkWebCert.csr -CA myCACertificate.pem -extensions v3_srv -extfile ./server-ssl-extensions.cnf -CAkey myCAPrivateKey.key -CAcreateserial -out mySplunkWebCert.pem -days 1095
# enter the CA key password

3. Combine the files and check the signature

Order matters: server certificate first, then the authority certificate, then the key in the final file. The file must be PEM format.

bash
cat mySplunkWebCert.pem myCACertificate.pem > mySplunkWebCertificate.pem
cat mySplunkWebCertificate.pem mySplunkWebPrivateKey.key > myFinalCert.pem

$SPLUNK_HOME/bin/splunk cmd openssl verify -CAfile ./myCACertificate.pem ./mySplunkWebCertificate.pem
expected output
./mySplunkWebCertificate.pem: OK

If you use a third-party certificate instead of steps 1 and 2, start here: combine its server certificate, intermediate certificates and root (if required), in that order, into one PEM file, then add the private key to make the final file.

4. Install it on the management port

Edit the files in $SPLUNK_HOME/etc/system/local, never the ones in etc/default. Put these settings in server.conf:

server.conf
[general]
serverName = mysplunkenterpriseserver.mycompany.com

[sslConfig]
serverCert = /opt/splunk/etc/auth/sloccerts/myFinalCert.pem
requireClientCert = false
sslRootCAPath = $SPLUNK_HOME/etc/auth/sloccerts/myCACertificate.pem

and these in web.conf:

web.conf
[settings]
enableSplunkWebSSL = true
serverCert = /opt/splunk/etc/auth/sloccerts/myFinalCert.pem

Use your own server name and your own absolute path to myFinalCert.pem. Then restart splunkd, which interrupts searching on that instance, so schedule it:

bash
$SPLUNK_HOME/bin/splunk restart splunkd

5. Get the certificate you will paste into Observability Cloud

The guided setup in Step L asks for only the first certificate in the chain, which is the server certificate. This command prints just the first certificate from the combined file:

bash
$SPLUNK_HOME/bin/splunk cmd openssl x509 -in $SPLUNK_HOME/etc/auth/sloccerts/mySplunkWebCertificate.pem

Copy everything from -----BEGIN CERTIFICATE----- to -----END CERTIFICATE-----, with no key and no second certificate.

Step M~5 min

Verify the connection

  1. In Observability Cloud, open Log Observer, choose your new connection and an index you allowed, and run a search over the last hour. You should see events from Splunk Enterprise.
  2. On the search head, as an administrator, confirm the searches arrive from the service account. This reads Splunk's audit index, which the service account itself cannot read:
SPL on the search head
index=_audit action=search user=<your_service-account_name> | head 10

Each Log Observer search should produce about four back-end searches under that account. If you see them, the connection works end to end.

Adapting for a customer cluster

  • Token handling. Helm records the values it was installed with in a Secret in the release namespace, so a token passed with --set-string is readable by anyone who can read Secrets there. For anything beyond a lab, load the token from a Kubernetes Secret or your secrets manager and use short-lived tokens.
  • Their own services. The demo shows the Collector side. For the customer's real workloads, point their existing OTLP exporters at the in-cluster Collector service instead of at Splunk, which keeps the token in one place. See the debrief table for the trade-offs.
  • Egress. Only the Collector pods need outbound HTTPS to ingest.<realm>.signalfx.com or ingest.<realm>.observability.splunkcloud.com.
  • Sensitive data. Add a redaction processor to the Collector before export, and agree the attribute list with the security team first.
  • Environment names. Use a clear deployment.environment per cluster, with consistent casing.

Diagnostics

Test the ingest endpoint directly

bash
curl -i -X POST "https://ingest.${REALM}.signalfx.com/v2/trace/otlp" \
  -H "X-SF-Token: ${ACCESS_TOKEN}" -H "Content-Type: application/x-protobuf"

Any HTTP response proves the network path to the endpoint works. A 401 points to the token. This sends an empty request, so a non-success status other than 401 is not necessarily a problem.
