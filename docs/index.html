0 · Briefing

The customer. Northstar Payroll (fictional) runs payroll, benefits and HR services. OpenTelemetry is already instrumented across most of the stack. They have an endpoint and a token and want to see traces in Splunk Observability Cloud.

The question. Two valid designs:

Your mission. Stand up the same seven-service app both ways, prove data lands in the right place, then answer: which design do you recommend to a regulated customer, and why?

The app you will run

Seven instrumented services plus six systems that appear as inferred nodes in the service map. The code is the same in both modes. Only environment variables change.

portal-web ─┬─► payroll-api ─┬─► tax-engine
            │                ├─► payroll-db          (inferred database)
            │                ├─► ach-gateway ─► bank-network   (inferred external)
            │                └─► notification-svc
            ├─► benefits-api ─┬─► benefits-db        (inferred database)
            │                 └─► carrier-gateway    (inferred external)
            └─► hr-api ───────┬─► hr-db              (inferred database)
                              └─► quickbooks-api     (inferred, third party)
  • Tenants are opaque ids (tenant-0001 to tenant-0012), which is how a multi-client accountant portal would tag requests.
  • About 20% of runs are multi-state, which makes tax-engine slow. About 6% of ACH submissions time out at the bank.
  • Spans carry deliberately fake sensitive fields: employee.ssn (invalid 900- range), bank.account_number and bank.routing_number (zeros). You will redact them in Challenge 3.
Lab status. The SDK-direct path was run against a real us1 org and the data was confirmed in APM (all seven services and six inferred nodes). The Collector path is written to the same spec but has not yet been run end to end; treat Challenge 2 as the first live test of it.

1 · Before you start

You need

  • A Splunk Observability Cloud org and its realm. This lab uses us1. Find yours under your profile in the UI.
  • An org access token with the INGEST scope. Settings → Access Tokens → New Token → scope Ingest. Nothing else is needed to send data. Do not use an API-scope token for ingest.
  • Either Docker (Desktop or Engine) or Python 3.10+.

Get the lab

git clone https://github.com/garrett-splunk/otel-uptream-fsi-guide.git
cd otel-uptream-fsi-guide
cp .env.example .env

Where the token goes

Open .env and set the two values:

SPLUNK_REALM=us1
SPLUNK_ACCESS_TOKEN=<your ingest token>
This repo is public. .env is git-ignored. Never paste a token into an HTML, YAML or script file, and never commit one. If a token leaks, rotate it in Settings → Access Tokens. Use a short-lived token for workshops.

3 · Challenge 1: SDK direct

Mission Get all seven services sending straight to us1, with no Collector anywhere.

How it is wired

The services use the upstream OpenTelemetry Python SDK, not a Splunk distribution. The exporter reads standard OTel environment variables, so nothing about Splunk is in the code:

app/telemetry.py   →  OTLPSpanExporter()  and  OTLPMetricExporter()   (no arguments)
VariableValue in direct mode
OTEL_EXPORTER_OTLP_PROTOCOLhttp/protobuf
OTEL_EXPORTER_OTLP_TRACES_ENDPOINThttps://ingest.us1.observability.splunkcloud.com/v2/trace/otlp
OTEL_EXPORTER_OTLP_METRICS_ENDPOINThttps://ingest.us1.observability.splunkcloud.com/v2/datapoint/otlp
OTEL_EXPORTER_OTLP_HEADERSX-SF-Token=<your ingest token>
OTEL_SERVICE_NAMEone per service, for example payroll-api
OTEL_RESOURCE_ATTRIBUTESdeployment.environment=fsi-workshop-direct,service.version=1.0.0
Why the full URLs matter. When you set the signal-specific variable (..._TRACES_ENDPOINT), the SDK uses it exactly as written. If you set only the generic OTEL_EXPORTER_OTLP_ENDPOINT, the SDK appends /v1/traces, which is not Splunk's ingest path. That is the most common reason direct export silently fails.

deployment.environment is what puts the data under an environment in APM. Leave it out and the services show up without a usable environment filter.

Run it

With Docker:

./run.sh direct

Without Docker (runs the seven services as local Python processes for 2 minutes):

./run-local.sh 120

What the script does, step by step:

  1. Loads .env and refuses to start if the token is still REPLACE_ME.
  2. Builds the traces and metrics URLs from SPLUNK_REALM.
  3. Sets OTEL_EXPORTER_OTLP_HEADERS=X-SF-Token=... and deployment.environment=fsi-workshop-direct for every service.
  4. Starts the services and a traffic generator that posts payroll, benefits and HR requests for twelve synthetic tenants.

Predict, then verify

Predict firstThen check in Splunk
How many services will appear in the map? How many are inferred?APM → Service Map, environment fsi-workshop-direct. Expect 7 instrumented services and 6 inferred nodes.
Which two nodes are databases you never instrumented?Look for postgresql:payroll-db, postgresql:benefits-db, postgresql:hr-db. The app only emits client spans with db.system and db.name.
Which hop is slowest?Click tax-engine. p90 should be far above p50 (a long tail from multi-state runs).

Checkpoint. You pass Challenge 1 when the environment fsi-workshop-direct shows all seven services and a trace from portal-web spans at least four services.

UI labels vary a little between releases. If a menu is not where described, use the search box and the environment filter.

4 · Challenge 2: Collector

Mission Move the token out of the apps. Run the same services through a gateway Collector.

What changes

  • The apps point at the Collector (http://otel-collector:4318) and carry no token.
  • The Collector holds the token and forwards to the same us1 endpoints.
  • The app code, the container image and the traffic are identical. Only the environment variables differ.

The Collector config

File: collector/config.yaml (upstream otel/opentelemetry-collector-contrib, pinned to 0.116.0).

exporters:
  otlphttp/splunk:
    traces_endpoint: https://ingest.${env:SPLUNK_REALM}.observability.splunkcloud.com/v2/trace/otlp
    metrics_endpoint: https://ingest.${env:SPLUNK_REALM}.observability.splunkcloud.com/v2/datapoint/otlp
    headers:
      X-SF-Token: ${env:SPLUNK_ACCESS_TOKEN}

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, attributes/redact, batch]
      exporters: [otlphttp/splunk, debug]
Exporter name. Upstream 0.116.0 calls the exporter otlphttp. Splunk's own Collector distribution is renaming it to otlp_http. If you switch to the Splunk distribution later, change the name, not the URLs.

Run it

./run.sh down direct      # stop Challenge 1 if it is still running
./run.sh collector

This sets the environment to fsi-workshop-collector. You can run both modes side by side if you want to compare them in one map: use ./run.sh direct in one terminal and ./run.sh collector in another, since each uses its own Docker project name.

Predict, then verify

Predict firstThen check
Will the service map look different from Challenge 1?It should be identical in shape, under environment fsi-workshop-collector.
Where would you look if nothing appears?docker compose -p fsi-collector logs otel-collector. The debug exporter prints a line per batch, and the exporter prints HTTP errors such as 401.
How many places now hold the token?One. Run grep -r SPLUNK_ACCESS_TOKEN docker-compose.yml and confirm only the otel-collector service references it.

Checkpoint. Environment fsi-workshop-collector shows the same seven services, and no app container has the token in its environment.

5 · Challenge 3: Redaction

Mission Payroll data includes SSNs and bank details. Make sure none of it reaches a SaaS backend, and compare how hard that is in each mode.

Three services add fake sensitive attributes: employee.ssn, bank.account_number and bank.routing_number. The values are synthetic (900-00-0001, 0000012345, 000000000).

  1. Find the leak (direct mode). In fsi-workshop-direct, open any payroll-api trace, then the span for POST /payroll/run. You should see employee.ssn in clear text.
  2. Fix it in the app. Set REDACT_IN_SDK=true in .env and restart direct mode. The code path is telemetry.tag_sensitive(). Every service team must call it correctly for every sensitive field. Check a new trace: the value is ***REDACTED***.
  3. Fix it centrally (Collector mode). With REDACT_IN_SDK=false, run ./run.sh collector. The attributes/redact processor deletes the three keys for every service. Open a trace in fsi-workshop-collector: the keys are gone, even though the app still sets them.

Discuss. Which control would a security reviewer rather audit: forty services each masking correctly, or one reviewed Collector rule set? What happens when a developer adds a new sensitive field next quarter?

A Collector rule set deletes attributes by name. It will not catch sensitive data in a field you did not list, or in a span name or a URL. Treat it as a safety net, not a substitute for not collecting data you do not need.

6 · Challenge 4: Find the fault

Mission A client says payroll runs are slow and occasionally fail. Use the data to find out why.

  1. Open the map in either environment. Which service has the worst p90 latency?
  2. Open Traces and filter by payroll.jurisdiction. Compare single-state against multi-state. Which one explains the slow requests?
  3. Filter for errors. Follow a failed trace from portal-web down. Where does the error start? Look for the bank-network client span with status 504.
  4. Use client.tenant_id to check whether one client is hit harder than the others. (With random traffic, expect no strong pattern. In a real accountant portal this is how you would find a client-specific problem.)
You should findCause built into the lab
Slow tax-engine, long tailMulti-state runs take 0.8 to 1.5 s instead of 30 to 90 ms.
Intermittent 502 from payroll-apiach-gateway times out about 6% of the time because bank-network (external) is slow.
Occasional failure on HR summaryquickbooks-api (third-party integration) fails about 3% of the time.

This is the business case in miniature: the service map and trace tags answer "which dependency, which tenant, which hop" without log searching.

7 · Challenge 5: Metrics (optional)

Two custom metrics are exported the same way as traces: payroll_runs (counter, tagged result) and ach_settlement_seconds (histogram). Standard HTTP server and client metrics come from the instrumentation libraries.

  • Direct mode sends metrics to /v2/datapoint/otlp with the same header.
  • Collector mode sends them to the Collector's /v1/metrics, which forwards them to /v2/datapoint/otlp.

Verify. In Metric Finder, search for payroll_runs. Chart it, split by result and by the deployment.environment dimension. Compare the two environments.

The lab exports cumulative counters. If your own services use delta temporality, confirm the backend behaviour before relying on a rate chart.

8 · Debrief: which one?

You now have evidence for both. Use it to fill in the decision table for your own environment.

QuestionSDK directVia Collector
Where does the token live?On every host or container that runs a serviceOn the Collector only
Outbound firewall rulesEvery service host needs an allow to ingestOne egress point
Redaction and attribute rulesIn app code, per teamOne central rule set
Change a destination or add a second backendRedeploy every serviceEdit the Collector config
Buffering and retry if the backend is unreachableSDK queue only; data can be dropped on restartCollector queue and retry (add persistent storage for more)
Extra moving partsNoneA service to run, size and patch
Host and infra metricsNot collectedCollector can collect them
Fastest path to a proof of conceptYes: two env varsOne extra container

A reasonable default for a regulated customer

  • Proof of concept in one environment: SDK direct is fine and fastest, as long as the token is scoped to ingest and short lived.
  • Anything beyond that: a gateway Collector. One egress path, one place to redact, no tokens in application config.

The code does not change between the two, which is the point: you can start direct and move to a Collector by changing environment variables.

9 · Troubleshooting

SymptomLikely cause and fix
Nothing in APM after 2 minutesWrong realm, or the environment filter in APM is set to something else. Check SPLUNK_REALM and select fsi-workshop-direct or fsi-workshop-collector.
HTTP 401 or 403 in service or Collector logsToken missing, mistyped, expired, or not an ingest-scope token. Create a new ingest token and update .env.
Connection errors or timeoutsA proxy or firewall is blocking outbound 443 to ingest.<realm>.observability.splunkcloud.com. Any HTTP response from that hostname proves the network path works.
Data arrives but nothing links across servicesContext is not being propagated. In this lab it is handled by the requests instrumentation. In your own services, check that W3C trace context headers are forwarded.
Traces arrive but the SDK sends to /v1/tracesYou set OTEL_EXPORTER_OTLP_ENDPOINT instead of the signal-specific variable. Use OTEL_EXPORTER_OTLP_TRACES_ENDPOINT with the full URL.
Database or external node missing from the mapThe client span needs db.system and db.name (databases) or peer.service (external systems).
Collector rejects the configCheck the exporter name for your Collector build (otlphttp upstream 0.116.0, otlp_http in newer Splunk distributions).

10 · Clean up

./run.sh down direct
./run.sh down collector
  • Delete or rotate the access token you used (Settings → Access Tokens).
  • The sandbox data ages out by itself. Nothing in this lab is real customer data.
